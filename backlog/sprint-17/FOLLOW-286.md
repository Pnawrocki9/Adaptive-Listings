## Defects to Fix

### CB-1 (P1 runtime) — PostgREST `on_conflict` placement

`intent-snapshot.ts` sends `on_conflict=tenant_id,session_id` inside the `Prefer` header. PostgREST
takes `on_conflict` exclusively as a URL QUERY PARAMETER:

```
POST /rest/v1/intent_sessions?on_conflict=tenant_id,session_id
Prefer: resolution=merge-duplicates,return=minimal
```

As currently written, the conflict target is never parsed by PostgREST. The 2nd+ snapshot per
`(tenant_id, session_id)` hits the `intent_sessions_tenant_session_unique` constraint and
returns 409. The handler discards this via `Promise.allSettled`, freezing the `intent_sessions` row
at first-snapshot state for the entire session. This is the first PostgREST upsert in the repo — no
prior art or parity gate.

**Fix:** Move `on_conflict=tenant_id,session_id` from the `Prefer` header to the URL query string.

### LG-1 (P1) — ClickHouse `event_type` vocabulary mismatch

`intent-snapshot.ts:156` writes `event_type: 'intent.snapshot'`. The 0014 DDL documents a
`LowCardinality` vocabulary of `quiz_answer|chat_turn|behavioral|dwell|pageview|referrer|finalized`
(lines 17-19). FOLLOW-269 will `GROUP BY event_type` against this vocabulary.

**Fix:** Either map to a documented value (using `last_signal_delta.event_type` from the payload),
or add `'intent.snapshot'` / `'snapshot'` to the DDL vocabulary AND pin both sides to a shared
constant in `@estalara/shared` so they cannot diverge again.

### LG-2 (P1) — `intent_session_id` join key

`deriveSessionUuid()` produces a SHA-256→UUID-v4-layout value for `intent_events.intent_session_id`.
`intent_sessions.id` is generated by `gen_random_uuid()`. These will never match — the FK join the
0014 DDL documents (FOLLOW-269 replay) will always return empty results.

**Fix:** Carry the raw `session_id` string (or `(tenant_id, session_id)` composite) on
`intent_events` so FOLLOW-269 can join the two stores. OR correct the DDL FK claim to document that
the join is by `(tenant_id, session_id)` string, not by UUID.

### TG-1 (P1) — Missing contract tests

All 18 existing tests assert mock-call shapes (which arguments were passed to the mock). None assert
the REAL contract. Add tests that verify:

1. The PostgREST upsert URL carries `?on_conflict=tenant_id,session_id` (not in the `Prefer` header)
2. The written `event_type` value is within the 0014 vocabulary
3. A 2nd snapshot for the same `(tenant_id, session_id)` triggers an UPDATE (not a 409 rejection)

These are Rule Q request-contract tests, not mock-call-shape tests.

### LG-3 (P2) — `confidence_before` hardcoded `0`

`confidence_before` is hardcoded to `0` for every snapshot. This collapses the before/after delta
that the `intent_events` table exists to capture for replay/training.

**Fix:** Resolve the prior confidence from:

- The SDK-supplied `confidence_before` field in the payload (if the Phase-3 SDK emits it), OR
- A server-side last-value lookup from the previous ClickHouse row for this session, OR
- Document that `confidence_before` is intentionally dropped for snapshot rows (and remove the
  column from the INSERT, or write NULL instead of 0) — whichever approach is chosen, record the
  decision.

### DG-1 (P2) — Stale handler JSDoc

`upsertIntentSessionToSupabase` has a 30-line JSDoc describing an
RPC/atomic-increment/SELECT-fallback path. The actual code is a single payload-passthrough POST.
Rewrite the JSDoc to match the code and cite the LG-4 trade-off decision.

### LG-4 (P2) — Type duplication (Rule J mirror)

`IntentSnapshotPayload` is hand-redeclared in `intent-snapshot.ts:52` AND inline at `events.ts:200`.
Import the shared type from `@estalara/shared`
(`packages/shared/src/schemas/events/intent-snapshot.ts`) instead of maintaining parallel copies.
