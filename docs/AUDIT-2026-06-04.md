## 1. Executive Summary

Adaptive Listings is **conditionally viable for a controlled pilot** but is not yet a complete
product. The behavioral observation layer, A/B holdout infrastructure, playbook-based copy
adaptation, and Bayesian intent engine are real and well-engineered. The description-generation
pipeline (LLM + Redis cache) is real but has a critical production grounding gap. The chat signal
integration that v1.0 requires does not exist in this repo. The DOM adaptation path for the actual
pilot site (app.estalara.com) depends on a handoff to a separate repo that has not been verified as
deployed.

**Verdict: 🟡 YELLOW**

**≈52% of Master_Design scope is built; the next planned step is completing the chat/live-signup
signal bridge (CHAT-001/002/003/SCHEMA-001) and verifying `PUBLIC_ESTALARA_SDK_ENABLED=true` is live
on app.estalara.com.**

**Top 5 reasons for YELLOW:**

1. Chat NLP integration (primary discriminating signal for 14/18 archetypes per §D.6) = 28-line
   placeholder. `apps/intent-engine/src/main.py` returns `{"status": "placeholder"}`.
2. Production description grounding silently fails. ESC-019 (OPEN): `ESTALARA_BACKEND_URL` →
   `https://app.estalara.com` redirects to login, `original_description` is always `''`, LLM
   generates ungrounded copy.
3. DOM adaptation on app.estalara.com depends on `data-estalara-slot` hooks added in the
   Estalara-app repo (separate repo), behind `PUBLIC_ESTALARA_SDK_ENABLED=true` flag. No
   confirmation this is deployed in production.
4. DSR mutation-poll cron was removed from `vercel.json` — GDPR Art. 17 ClickHouse erasure mutations
   never advance to done without manual intervention.
5. 15 of 18 archetypes are signal-blind in practice: only `scroll.depth`, `listing.viewed`, and
   `cta.clicked` produce behavioral updates, and none meaningfully distinguish more than 3
   archetypes.

## 4. Findings by Severity

### 4.1 Bugs and Logic Errors

**F-01 | Severity: High | Layer: Data Collection / GDPR**

- **File:** `packages/sdk/src/core/events.ts:54`
- **What's wrong:** `consent_state` in every ingest payload is hardcoded to `'legitimate-interest'`
  when `config.consentState !== 'opted_out'`. A visitor who explicitly grants consent via the banner
  is tagged identically to one who hasn't seen the banner yet. The schema declares a `'consented'`
  value but the SDK never emits it.
- **Why it matters:** GDPR audit trail is broken — the ingest log cannot distinguish "consented"
  from "not yet asked", which undermines the LIA justification and complicates any DPA audit.
- **Proposed fix:** Map `getConsentState()` result to the ingest enum: `'granted' → 'consented'`,
  `'pending' → 'legitimate-interest'`, `'denied' → 'none'`. Effort: **S**

**F-02 | Severity: High | Layer: DOM Adaptation**

- **File:** `packages/sdk/src/core/adapt.ts:311`
- **What's wrong:** `applyTextDirective` queries
  `document.querySelectorAll('[data-estalara-slot="..."]')`. On app.estalara.com there are zero such
  elements (CHK-B confirmed). The `adapt.applied` event is never emitted; `adapt.skipped` fires with
  `reason: 'no_slot_elements'` instead. Adaptation is entirely dependent on hooks in the
  Estalara-app repo that cannot be verified from this repo.
- **Why it matters:** Without confirmed `data-estalara-slot` hooks in production, the entire
  adaptation layer is invisible to users. The pilot measures no adapted experience.
- **Proposed fix:** Confirm `PUBLIC_ESTALARA_SDK_ENABLED=true` in Estalara-app production. Effort:
  **S** (30 min verification), potentially **L** if flag not yet deployed.

**F-03 | Severity: High | Layer: Description Pipeline**

- **File:** `apps/control-plane/src/lib/listing-details.ts:50`, `apps/control-plane/.env.example:18`
- **What's wrong:** ESC-019 (OPEN): `ESTALARA_BACKEND_URL` points at a URL that returns HTTP
  302→login. `listing-details.ts:63` uses `redirect: 'manual'` (fixed in PR #196) but
  `res.status >= 300` returns `''` (fail-open). The description job generates text without any
  listing facts.
- **Why it matters:** Every description generated in production is ungrounded — the model invents
  facts rather than adapting the agent's actual copy. This is the most visible AI quality defect.
- **Proposed fix:** Provision an internal/unauthenticated backend URL for listing details OR a
  service token. Set in Vercel prod + Doppler as `ESTALARA_BACKEND_URL`. Effort: **M**

**F-04 | Severity: Medium | Layer: Analytics / Conversion**

- **File:** `packages/sdk/src/core/adapt.ts:243`
- **What's wrong:** `registerFeedbackListener` listens for
  `config.feedbackEvents ?? ['inquiry.completed']`. Per CEO decision (Master_Design v3.7), actual
  conversion events are `live.signup` OR `chat.contact_initiated`. Neither event is ever dispatched
  from `app.estalara.com`. The bandit feedback loop (`POST /api/adapt/feedback`) never fires for
  real conversions.
- **Why it matters:** Thompson sampling never receives positive outcome signals; all bandit arms
  accumulate only Beta(1,1) priors. The pilot CTA-lift measurement window will never get
  variant-level conversion attribution.
- **Proposed fix:** Implement SCHEMA-001 + CHAT-001/002 (CustomEvent hooks in Estalara-app) +
  CHAT-003 (SDK listener). Effort: **M**

**F-05 | Severity: Medium | Layer: ClickHouse SQL**

- **File:** `apps/control-plane/src/app/api/adapt/route.ts:348`
- **What's wrong:** `logDecisionAsync` escapes strings with `s.replace(/'/g, "\\'")`. The DSR helper
  (`clickhouse-dsr.ts:99`) correctly uses `''` doubling (ANSI SQL standard). Two different escaping
  strategies in the same codebase.
- **Why it matters:** Defense-in-depth and code quality concern. Not currently exploitable but
  fragile.
- **Proposed fix:** Standardize on `''` doubling across all ClickHouse raw SQL. Effort: **S**

### 4.2 Architectural / Conceptual Issues

**F-06 | Severity: High | Layer: Signal Coverage**

- **File:** `packages/sdk/src/core/intent.ts:239–255`
- **What's wrong:** `SIGNAL_LIKELIHOODS` defines meaningful discrimination only for 4 event types.
  The behavioral damping factor (0.3) further reduces each signal's impact. Practical result:
  without the quiz, a real visitor almost certainly remains classified as `neutral` (prior 0.37)
  throughout their session.
- **Why it matters:** For non-quiz users (the majority of anonymous visitors), confidence stays
  below the 0.6 threshold and `runDecisionTree` returns empty directives (`source: 'default'`). The
  adaptation never fires.
- **Proposed fix:** Implement FOLLOW-099 (5 new signal types) + FOLLOW-100 (chat NLP calibration).
  Short-term: lower `CONFIDENCE_THRESHOLD` to 0.4 for the pilot to force at least playbook-level
  adaptation. Effort: **M–L**

**F-07 | Severity: High | Layer: Chat Integration**

- **File:** `apps/intent-engine/src/main.py:1–28`
- **What's wrong:** `apps/intent-engine` is a 28-line stub returning `{"status": "placeholder"}`. No
  Redpanda consumer, no Haiku 4.5 NLP extraction, no `chat.intent.detected` emission. Per §D.6
  (Archetype Coverage Matrix), 5 archetypes have "🔴 None" coverage and others are "🟡 Chat-only".
- **Why it matters:** The product's core differentiator over naive A/B testing is real-time intent
  detection from conversation. Without the intent-engine, the system is a rule-based classifier with
  4 behavioral inputs.
- **Proposed fix:** FOLLOW-087 (Modal intent-engine, Haiku 4.5 real-time + Sonnet 4.6 batch).
  Depends on CHAT-001/002. Effort: **L**

**F-08 | Severity: Medium | Layer: Signal / State**

- **File:** `packages/sdk/src/index.ts:232`
- **What's wrong:** `refreshDirectives()` passes `pageType: 'listing_list'` hardcoded regardless of
  actual page. On a listing detail page the server always treats it as a grid view, resulting in
  ReorderDirective instead of detail slot directives.
- **Why it matters:** Incorrect page context means wrong directive type for the most important page
  in the funnel.
- **Proposed fix:** Detect page type from URL pattern (e.g. `/listing/` → `listing_detail`) or
  `data-page-type` attribute. Effort: **S**

**F-15 | Severity: Medium | Layer: DOM Adaptation / UX**

## 5. Conceptual Soundness Review

### Archetype Model Coherence

The 18-archetype Bayesian model in `intent.ts` is conceptually sound and well-engineered as a
pure-function classifier. Three structural weaknesses:

1. **Quiz is a 2-question binary classifier** (`purpose: investment|personal` ×
   `horizon: short|long`). This produces a 2×2 = 4 intent cells from which 18 archetypes must be
   distinguished. The resulting posterior is heavily underdetermined for archetypes that share the
   same purpose/horizon combination.

2. **Master_Design v3.7 reduced from 18 archetypes to 6 families** (D-3 ratified), but `intent.ts`
   and all playbook files still operate on 18 archetypes. The "6 families compatibility layer
   (dual-keyed bandit_arms)" referenced in v3.7 for FIX-018/019/020 is not visible in the current
   codebase. The 18→6 migration is planned but not yet executed.

3. **Signal coverage asymmetry** (per §D.6): 5 archetypes (`commercial_investor`, `diaspora_buyer`,
   `student_parent`, `golden_visa_buyer`, `retiree_relocator`) are classified 🔴 None — they can
   only be detected via chat signals that don't exist yet.

### Signal Sufficiency Analysis

With only 4 behavioral signals, the system's practical discrimination is:

- Reliable identification: `yield_hunter` (CTA click + listing view pattern), `portfolio_builder`
  (listing view density)
- Weak inference: `neutral` fallback for ~80% of sessions
- Unreachable archetypes: all 5 "🔴 None" archetypes; most "own use" archetypes without quiz

The quiz is the current workaround and meaningfully improves classification for users who answer.
The trigger threshold (3 listing views) is reasonable but means many bounce-session users never see
it.

### DOM Adaptation UX Risk Assessment

The MutationObserver `disconnect → write → reconnect` pattern in `adapt-description.ts` is
technically correct and addresses the SvelteKit reconciliation problem from PR #195 (FOLLOW-189).
The `rafPending` flag prevents rAF storms. However, `resetAdaptState()` being called on every
`refreshDirectives()` invocation (F-15) means re-writes occur every ~30 seconds of engagement, which
may produce visible flicker.

### Measurement Plan Assessment

The CTA-lift dashboard (`/dashboard/pilot`) was hardened to fail loud and show `data_source`
provenance (FOLLOW-122). Thompson sampling variant selection is wired end-to-end. The core problem
is that the primary conversion events (`live.signup`, `chat.contact_initiated`) are not yet emitted
by the site, so the bandit will never receive true positive labels during the pilot.

## 10. Addendum — Follow-up Analysis (2026-06-04/05, session 2)

### 10.1 Quiz — Full Assessment + Cascading Decision Tree Redesign

#### What is currently built (verified in code)

The quiz exists and is wired into the Bayesian engine:

- `packages/sdk/src/ui/quiz-widget.ts` — 2-step flat widget in Shadow DOM, 3 languages (en/pl/es)
- `packages/sdk/src/ui/quiz-trigger.ts` — sticky pill; fires after **3 listing views** on listing
  detail page only; 24h dismissal cooldown via localStorage
- `packages/sdk/src/core/intent.ts:141–222` — `QUIZ_LIKELIHOODS` with `purpose` and `horizon` axes;
  multiplied into Bayesian prior
- `packages/sdk/src/core/intent.ts:264` — `QUIZ_CONFIDENCE_BONUS = 1.2` (+20% confidence when
  answered)
- `apps/control-plane/src/app/api/quiz/config/route.ts` — `QuizConfig` schema with
  `enabled: boolean` field (defaults `false`); persists to `tenants.quiz_config` JSONB

The quiz was **omitted from Section 6.1** of the original audit — correction: status should be
**Done but redesigned** (functional code exists, but the approach is being replaced by the cascading
decision tree described below).

#### Two fundamental problems with the current design

**Problem 1 — Wrong trigger context.** The quiz fires only on listing detail pages after 3 views.
But the investor may land on a listing that doesn't fit them at all — so their answers are
contaminated by the specific property shown ("is this the right listing?" rather than "what kind of
investor am I?"). Cold-start requires generic questions answered before seeing listings.

**Problem 2 — Overlapping weights produce ambiguous leaves.** The current flat Q1×Q2 produces 4
classification cells for 18 archetypes. The `investment + long horizon` cell alone contains 5
archetypes with posterior products within 9% of each other — behavioral signals at
`BEHAVIORAL_DAMPING = 0.3` cannot resolve the tie.

#### New design: cascading decision tree (CEO spec, 2026-06-05)

**Trigger:** 30 seconds on any page where the SDK is loaded (listing list OR listing detail). Not
gated on listing views. Fires once per session; dismissal stored in `localStorage` with 24h
cooldown. **Controlled by `QuizConfig.enabled` toggle in admin panel (already exists).**

**Structure:** Gate question Q1 routes into 3 independent branches. Each branch has its own Q2, and
some have a Q3. Variable length: 2–3 questions depending on path. Every path ends at exactly one
archetype (a leaf node), except the "don't know" gate skip → `neutral`.

```
Q1 — GATE (always shown)
"Czego szukasz?"

  A. "Nieruchomość, która będzie na siebie zarabiać"  → branch: INWESTOR
  B. "Miejsce do mieszkania dla mnie lub rodziny"      → branch: WŁASNY UŻYTEK
  C. "Nowe miejsce w innym kraju lub nowy etap życia"  → branch: CROSS-BORDER
  D. "Jeszcze nie wiem — pokaż mi oferty"             → neutral (quiz ends, no adaptation)
```

#### Change to the intent engine: direct assignment, not weight multiplication

The current `applyQuizPrior()` multiplies likelihood vectors into the Bayesian prior. With a
decision tree that produces a single leaf archetype, the correct approach is **direct assignment**
at high confidence:

```typescript
// New function to add to intent.ts
export function applyQuizLeaf(state: IntentState, archetype: Archetype): IntentState {
  // Set the leaf archetype to near-certainty; distribute residual across all others
  const probabilities = Object.fromEntries(
    ARCHETYPE_NAMES.map((k) => [k, k === archetype ? 0.85 : 0.15 / (ARCHETYPE_NAMES.length - 1)]),
  ) as ArchetypeProbabilities;
  return {
    archetype,
    confidence: Math.min(0.85 * QUIZ_CONFIDENCE_BONUS, 1.0), // ~0.95 confidence floor
    probabilities,
    signal_count: state.signal_count,
    last_updated_at: Date.now(),
    quiz_answered: true,
  };
}
```

Keep `applyQuizPrior()` as a fallback for future partial-signal paths. `applyQuizLeaf()` is called
when a complete path terminates at an unambiguous leaf.

#### Post-quiz archetype confidence, drift detection, and session override

**Design principle:** The quiz result is the strongest available prior, but it is not final.
Behavioral signals and chat analysis can both reinforce and correct it — within a single session,
without touching the permanent `description_cache_persistent` table.

---

**What already exists in the code (verified):**

- `intent.ts:491` — `detectMismatch(quizArchetype, behavioralState, sessionId)`: compares
  quiz-resolved archetype against behavioral-only state. Returns a `MismatchEvent` when:
  - `signal_count ≥ 3` (MISMATCH_MIN_SIGNALS)
  - The behavioral archetype differs from the quiz archetype
  - Either opposing group probability > 0.4 (`MISMATCH_OPPOSING_THRESHOLD`) OR confidence gap > 0.3
    (`MISMATCH_GAP_THRESHOLD`)
- `intent.ts:538` — `calculateBehavioralOnlyState(signalHistory)`: recalculates archetype from pure
  behavioral signals with no quiz prior; used inside mismatch detection
- `index.ts:379–398` — mismatch is **detected and logged** (dispatches `quiz.mismatch` ingest
  event), then `refreshDirectives()` is called — but the current code does **not** act on the
  mismatch: the session archetype stays as the quiz result regardless

**The gap:** `detectMismatch()` produces a finding but the SDK discards it. No mechanism exists to
switch `currentIntentState.archetype` during a session even when evidence is overwhelming.

---

**Required behaviour (from CEO spec, 2026-06-05):**

```
Quiz fires
  │
  └─ applyQuizLeaf() → currentIntentState.archetype = QUIZ_ARCHETYPE (confidence ~0.95)
                      │
                      │  description_cache_persistent[listing × QUIZ_ARCHETYPE] ← permanent, never changed
                      │
  ┌─────────────────────────────────────────────────────────────────────┐
  │  Ongoing session signals (behavioral + chat)                        │
  │                                                                     │
  │  REINFORCE path:                                                    │
  │    signals agree with QUIZ_ARCHETYPE                                │
  │    → applyBehavioralSignal() keeps QUIZ_ARCHETYPE on top            │
  │    → confidence may rise above 0.95 (capped at 1.0)                │
  │    → no change, existing adaptation stays                           │
  │                                                                     │
  │  CONTRADICT path:                                                   │
  │    signals point to DRIFT_ARCHETYPE ≠ QUIZ_ARCHETYPE                │
  │    → detectMismatch() fires when gap threshold met                  │
  │    → sustained over N consecutive refreshes (DRIFT_HOLD_COUNT = 3) │
  │    → currentIntentState.archetype ← DRIFT_ARCHETYPE                │
  │    → refreshDirectives() fetches new directives for DRIFT_ARCHETYPE │
  │    → if description_cache_persistent[listing × DRIFT_ARCHETYPE]    │
  │        exists → immediate description swap                          │
  │      else → template_fallback + Modal job enqueued                  │
  │                                                                     │
  │  description_cache_persistent[listing × QUIZ_ARCHETYPE] UNCHANGED  │
  │  (used for cold-start of the NEXT session, and for all other users) │
  └─────────────────────────────────────────────────────────────────────┘
```

**Anti-thrash guard — `DRIFT_HOLD_COUNT = 3`:** A single contradicting signal must not trigger an
archetype switch (a user may click one unrelated CTA). The mismatch must be confirmed across 3
consecutive `refreshDirectives()` cycles before `currentIntentState` is overridden. A counter
`driftCandidateCount` is incremented on each consecutive mismatch and reset to 0 when signals
realign.

```typescript
// New state in index.ts (module-level, alongside quizTriggered)
let driftCandidateArchetype: Archetype | null = null;
let driftCandidateCount = 0;
const DRIFT_HOLD_COUNT = 3;

// Inside refreshDirectives(), after mismatch detection:
if (mismatch) {
  if (driftCandidateArchetype === mismatch.behavioral_archetype) {
    driftCandidateCount++;
  } else {
    driftCandidateArchetype = mismatch.behavioral_archetype;
    driftCandidateCount = 1;
  }
  if (driftCandidateCount >= DRIFT_HOLD_COUNT) {
    currentIntentState = applyQuizLeaf(currentIntentState, driftCandidateArchetype);
    driftCandidateArchetype = null;
    driftCandidateCount = 0;
    // refreshDirectives() will re-run with the new archetype on the next cycle
  }
} else {
  // Signals realigned — reset drift counter
  driftCandidateArchetype = null;
  driftCandidateCount = 0;
}
```

**Chat NLP as an override signal:** When `apps/intent-engine` (FOLLOW-087) is implemented, it will
emit `chat.intent.detected` events carrying an `archetype` suggestion. These are fed into
`applyBehavioralSignal()` like any other event — but with higher likelihood weights because chat is
the strongest signal. Once weighted correctly in `SIGNAL_LIKELIHOODS`, chat signals will naturally
accumulate toward `MISMATCH_GAP_THRESHOLD` faster than scroll/click signals.

Important: chat override is session-only. The `quiz_completions` row retains the original quiz path
permanently (MOAT data).

---

**When quiz is disabled (admin toggle OFF):**

```
Page load
  │
  └─ initIntentState() → currentIntentState.archetype = 'neutral' (BASE_PRIOR)
     │
     │  No quiz, no strong prior
     │
  ┌───────────────────────────────────────────────────────────────────┐
  │  Behavioral signals accumulate via applyBehavioralSignal()        │
  │  Chat signals accumulate via chat.intent.detected (FOLLOW-087)   │
  │  Dwell signals accumulate via applyDwellSignal() (FOLLOW-190)    │
  │                                                                   │
  │  refreshDirectives() runs every 5 signals:                       │
  │    if confidence < CONFIDENCE_THRESHOLD (0.6):                   │
  │      → source: 'default', no adaptation, user sees neutral DOM   │
  │    if confidence ≥ CONFIDENCE_THRESHOLD:                         │
  │      → normal adaptation path fires for first time               │
  │      → description_cache_persistent[listing × archetype] looked up│
  └───────────────────────────────────────────────────────────────────┘
```

Effect: without quiz, the system stays in `neutral` (no adaptation) until enough evidence
accumulates. On a typical listing page with behavioral-only signals (no chat), this may take 5–10
minutes of active engagement. With chat active (FOLLOW-087), identification can happen in 1–2
messages. The user experience degrades gracefully — they always see a valid (neutral/default)
listing, never a broken one.

**`CONFIDENCE_THRESHOLD` for pilot:** Currently `0.6` in
`apps/control-plane/src/app/api/adapt/route.ts:64`. With quiz disabled, consider lowering to `0.4`
(tunable per-tenant via config) to allow adaptation to fire earlier on partial behavioral evidence,
accepting slightly lower archetype precision. This is a pilot decision.

### 10.3 Permanent Description Cache — Redesign (No Tiers, No TTL)

#### Current state (verified in code) — what needs to change

`apps/control-plane/src/lib/description-cache.ts` implements Upstash Redis cache keyed as
`desc:{tenant_id}:{listing_id}:{archetype}:{locale}` with:

- `TTL_TIER2_SECONDS = 259200` (72h)
- `TTL_TIER3_SECONDS = 172800` (48h)

`apps/control-plane/src/app/api/adapt/description/route.ts:82` has `tier: z.enum(['1', '2', '3'])`
in the Zod request schema. The route branches on `tierNum` to choose TTL and Modal priority.

**Decision (CEO, 2026-06-05):** Adaptive Listings has no Tiers. Every tenant gets the same single
experience. The Tier-gating code is legacy and must be removed. The Redis TTL model is also
eliminated: **a description+headline generated for a listing×archetype must persist permanently — no
automatic expiry — until the listing is updated or deactivated.**

#### Required changes

**1. New Postgres table: `description_cache_persistent`**

```sql
CREATE TABLE description_cache_persistent (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id       text NOT NULL,
  listing_id      text NOT NULL,
  archetype       text NOT NULL,
  locale          text NOT NULL DEFAULT 'pl',
  description     text NOT NULL,
  headline        text,
  model           text NOT NULL,   -- e.g. 'claude-sonnet-4-6'
  generated_at    timestamptz NOT NULL DEFAULT now(),
  invalidated_at  timestamptz,     -- null = still valid
  UNIQUE (tenant_id, listing_id, archetype, locale)
);
-- RLS: tenant_id isolation
```

No TTL column. Invalidation is explicit (timestamp), not time-based.

**2. Lookup order in `apps/control-plane/src/app/api/adapt/description/route.ts`**

```
1. Query description_cache_persistent WHERE tenant_id=$1 AND listing_id=$2
     AND archetype=$3 AND locale=$4 AND invalidated_at IS NULL
   → if found: return { source: 'ai_cached', description, headline }

2. Check Upstash Redis key desc:{tenant}:{listing}:{archetype}:{locale}
   (kept as hot-path fast cache; populated by Modal on first generation)
   → if found: return { source: 'ai_cached' }; async backfill description_cache_persistent

3. Return { source: 'template_fallback' } immediately
   + fire-and-forget: enqueue Modal job (no priority tiers — single queue)
```

**3. Remove Tier logic from `route.ts`**

- Remove `tier` from the Zod request schema (`z.enum(['1', '2', '3'])`)
- Remove `TTL_TIER2_SECONDS` / `TTL_TIER3_SECONDS` constants and their conditional logic
- Remove `tierNum === 3 ? { priority: 'high', max_tokens: 600 } : { max_tokens: 450 }` branch — use

**5. `apps/llm-gateway/src/jobs/generate_description.py`**

**6. `apps/control-plane/src/app/api/webhooks/listing-updated/route.ts`**

- Add:
  `UPDATE description_cache_persistent SET invalidated_at = NOW() WHERE listing_id = $1 AND tenant_id = $2`

### 10.5 Signal Enrichment Findings — Low-Cost, High-Discrimination Signals

Analysis of the archetype identification system (2026-06-05) identified five signals currently
absent from the SDK that would materially improve classification accuracy at minimal implementation
cost. All five have new tickets in Sprint 15 (FOLLOW-207 through FOLLOW-211).

#### Why the current signal set is insufficient

With `BEHAVIORAL_DAMPING = 0.3`, the effective probability shift per `cta.clicked` event for
`yield_hunter` is only +4.5% (raw +15% × 0.3). To cross the `CONFIDENCE_THRESHOLD = 0.6` from
`BASE_PRIOR` (neutral=0.37) on behavioral signals alone requires approximately 15 CTA click events —
unrealistic for a typical session. Only `yield_hunter` and `portfolio_builder` receive any
meaningful behavioral uplift from the current 4 signal types. The remaining 15 non-neutral
archetypes are effectively unreachable without quiz or chat.

The root cause: `SIGNAL_LIKELIHOODS` in `intent.ts:239` defines non-trivial overrides for only 3 of
17 non-neutral archetypes. The other 14 sit at baseline 1.0 for all signals — fully determined by
prior probability only. This is an incomplete table, not a calibrated model.

#### F-22 | Severity: High | Layer: Signal Coverage

- **File:** `packages/sdk/src/index.ts` (session init)
- **What's wrong:** `navigator.referrer` and UTM query params are never read at session init. A user
  arriving from Google "investment property Warsaw" has a near-certain investor archetype before
  interacting with anything. This free signal is completely ignored.
- **Why it matters:** Cold-start confidence stays at BASE_PRIOR (neutral=0.37) for the first 5–10
  behavioral events. Referrer capture moves the prior immediately at session start, compressing the
  cold-start window.
- **Proposed fix (FOLLOW-207):** Add `applyReferrerHints(state, referrer, utmTerm)` to `intent.ts`.
  Call at session init before `initIntentState()`. Parse `document.referrer` hostname + path +
  `utm_term`. Apply investment prior on keyword match. Effort: **S** (2h)

#### F-23 | Severity: High | Layer: Signal Coverage

- **File:** `packages/sdk/src/index.ts` (session init)
- **What's wrong:** Device type (mobile vs desktop) is not captured. Investor archetypes
  (`portfolio_builder`, `yield_hunter`, `commercial_investor`) significantly over-index desktop
  because investors browse alongside spreadsheets. Own-use buyers (`family_buyer`,
  `first_time_buyer`) split more evenly. This signal is available via `window.innerWidth` at zero
  cost.
- **Why it matters:** Weak signal alone but valuable as a session-init prior multiplier. Combined
  with referrer, it meaningfully narrows the cold-start uncertainty.
- **Proposed fix (FOLLOW-207, bundled):** Add `device_type: 'desktop'|'mobile'` to
  `SIGNAL_LIKELIHOODS`. Log in `session.started` ingest event. Effort: **S** (1h, bundled with F-22)

#### F-24 | Severity: High | Layer: Signal Coverage

- **File:** `packages/sdk/src/index.ts` (listing.viewed handler, line 341)
- **What's wrong:** `listing.viewed` counts page views but ignores rate. `listingViewCount` is
  tracked (for quiz trigger) but `sessionStartedAt` is not. Rate (views/min) is one of the strongest
  behavioral discriminators: `portfolio_builder` and `flip_investor` exhibit high-velocity
  comparison shopping (≥3 views/min, short dwell); `family_buyer` and `first_time_buyer` browse
  slowly (≤0.5 views/min, long dwell).
- **Why it matters:** Rate provides archetype discrimination that count alone cannot. A user who
  views 10 listings in 3 minutes is almost certainly not a first-time buyer — they are
  comparison-shopping as an investor.
- **Proposed fix (FOLLOW-208):** Add `applyListingViewRate(state, viewCount, elapsedMs)` to
  `intent.ts`. Call in `listing.viewed` handler when `viewCount ≥ 2`. Log `listing_view_rate` in
  `session.quality.snapshot`. Effort: **S** (3h)

#### F-25 | Severity: Medium | Layer: Signal Coverage

- **File:** `packages/sdk/src/ui/quiz-widget.ts` (complement to quiz)
- **What's wrong:** For the ~70–80% of sessions that do not complete the full quiz, there is
  currently no intermediate intent capture mechanism. Micro-polls (single yes/no questions) have
  ~60–70% completion rates in real estate UX vs ~20–30% for multi-question quizzes.
- **Why it matters:** Each micro-poll answer provides one Bayesian update equivalent to one
  `QUIZ_LIKELIHOODS` axis. Three sequential micro-polls approximate the discriminating power of the
  old 2-question flat quiz, with higher reach.
- **Proposed fix (FOLLOW-209):** New `packages/sdk/src/ui/micro-poll.ts` — bottom toast, not full

#### F-26 | Severity: High | Layer: Signal Coverage — FAVORITES

- **File:** app.estalara.com SvelteKit repo (ListingCard.svelte or listing detail page)
- **What's wrong:** app.estalara.com has a save-to-favorites feature. A user who favorites a listing
  is expressing high purchase intent — the strongest deterministic intent signal available outside
  of direct contact. No CustomEvent is dispatched when this happens. The SDK is completely blind to
  this action.
- **Why it matters:** Favoriting is the clearest behavioral signal of non-neutral intent. It pushes
  `neutral` probability down sharply and, when combined with listing metadata (bedrooms, type, price
  range), provides direct archetype inference. Unlike soft behavioral signals (scroll, CTA click), a
  favorite is an explicit user decision.
- **Proposed fix (FOLLOW-210):** Add
  `window.dispatchEvent(new CustomEvent('estalara:listing:favorited', {detail: {listingId, listingType, priceRange, bedroomCount}}))`
  to the favorites action in Estalara-app. SDK listener → `listing.bookmarked` ingest event +
  `applyBehavioralSignal`. Conditional payload-based archetype boosts. Effort: **M** (5h)

#### F-27 | Severity: High | Layer: Signal Coverage — FILTER PAYLOAD

- **File:** `packages/shared/src/schemas/events/` + `packages/sdk/src/core/intent.ts:239`
- **What's wrong:** `filter.applied` is planned in FOLLOW-099 but without a rich facet+value
  payload, it provides near-zero discrimination.
  `filter.applied({facet: "type", value: "commercial"})` is a near-certain `commercial_investor`
  signal. `filter.applied` without payload is equivalent to `scroll.depth` — it tells you someone
  interacted, not what they want.
- **Why it matters:** Filter facets are the most direct expression of buyer preferences available in
  behavioral data. Without defining the payload schema first, FOLLOW-099's `filter.applied`
  implementation will produce a useless event.
- **Proposed fix (FOLLOW-211):** Define `FilterAppliedPayload` Zod schema. Add facet-conditional
  likelihood updates to `applyBehavioralSignal` dispatch path. Effort: **S** (2h, but prerequisite
  for FOLLOW-099)

#### Note on BEHAVIORAL_DAMPING calibration

`BEHAVIORAL_DAMPING = 0.3` was chosen without empirical calibration. It was likely set
conservatively to prevent single-event archetype swings. At this value, even the new signals will
have limited per-event impact. Once pilot data accumulates (≥500 sessions with quiz completions), a
logistic regression fit on `(signal_vector → quiz_archetype)` should be run to calibrate both
`SIGNAL_LIKELIHOODS` values and `BEHAVIORAL_DAMPING`. Do not increase BEHAVIORAL_DAMPING before
calibrated likelihoods for all 17 archetypes are in place. New ticket: **FOLLOW-212** — post-pilot
likelihood calibration (P3, data-engineer + ml-engineer, requires ≥500 labeled sessions from pilot).
