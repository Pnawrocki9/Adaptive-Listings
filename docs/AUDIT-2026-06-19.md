## 1. Executive Summary

The foundation is sound and has improved markedly in the 15 days since the last audit. The
data-collection, consent/GDPR, ingest, decision-route, conversion-measurement, and admin-auth layers
are real, safe, and well-engineered. The codebase is **not** the problem. The problem is that
several pieces that **look done are hollow at the load-bearing center** — the parts that make a
buyer actually see a correct, personalized adaptation on real traffic. None of these are
architectural defects requiring rework; they are last-mile wiring and data-population gaps. But they
will not close by themselves, and the current queue is spending its cycles on P2/P3 hygiene tickets
rather than on them.

**Verdict: 🟡 YELLOW** — finish on this foundation, but only after closing five specific hollow-core
items. Continuing the current queue trajectory _as-is_ will not get you to "works as intended."

**Progress: ≈60% of Master_Design scope is built** (up from ≈52% on 2026-06-04). Basis: plumbing /
infrastructure layers are largely complete and the quiz-v2.0 / chat-producer / bandit /
conversion-label / tracer / admin-auth work landed since 06-04; the "intelligence actually works on
live traffic" layer plus several Master*Design promises (real affinity model, live chat adaptation,
multi-region, platform templates, WordPress plugin, pricing/billing, Tier 3) remain. The next
\_planned* queue step is merging PR #319 (FOLLOW-335) then promoting P3 hygiene stubs — none of
which address the five items below.

**Top 5 reasons for YELLOW:**

1. **Adaptation is invisible on un-instrumented pages.** The SDK only mutates DOM nodes carrying
   hand-coded `data-estalara-slot` attributes and _never self-annotates_ detected selectors at
   runtime (`packages/sdk/src/core/adapt.ts:465`). On the actual pilot site (app.estalara.com, a
   separate no-code repo) the hooks are committed but **not deployed** (ESC-020, still OPEN).
   Pipeline exists; buyer sees nothing. → **F-04**
2. **Card "personalization" is a hash, not affinity.** `archetype_embeddings.embedding` is seeded
   NULL (`packages/db/migrations/0005_seed_archetype_embeddings.sql`) and **no job to populate it
   exists anywhere in the repo**, so every adapt request falls through to a djb2 hash
   (`apps/decision-api/src/lib/reorder.ts:210`). Even a correct archetype yields hash-ordered
   listings. → **F-02**
3. **The bandit optimizes placebo arms.** Variant selection is now fully wired (selected → on the
   wire → learned → durable `conversion_labels`), but `runDecisionTree()` never receives the variant
   and `getPlaybook()` keys only on archetype, so control/v1/v2 serve byte-identical copy
   (`apps/control-plane/src/app/api/adapt/route.ts:909-925`). The A/B apparatus can never find a
   winner. → **F-03**
4. **Chat — the highest-value signal — is captured and discarded.** Real Haiku/Sonnet NLP exists on
   both ends, but nothing ever calls `process_chat_message`; the stream-consumer never routes
   `chat.message.sent` to it (`apps/intent-engine/src/main.py`, `apps/stream-consumer`). Shadow-only
   by design this sprint, so mitigated — but live chat adaptation does not function. → **F-05**
5. **No confidence floor before adaptation.** `refreshDirectives()` applies directives from the
   cold-start state with no gate on confidence or signal count (`packages/sdk/src/index.ts:643`);
   only the sidebar is gated at 0.6. A single referrer/device hint can reshuffle the DOM into a
   low-evidence archetype before any behavior. → **F-01**

The good news: every one of these is S/M effort, and the privacy/security posture (the thing that's
expensive to get wrong) is now solid.

## 4. Findings by Severity

### 4.1 Bugs and logic errors

**F-01 | High | Profile Engine — no confidence/signal floor before DOM adaptation.**
`packages/sdk/src/index.ts:643` (and init call at `:861`). `applyDirectives()` runs unconditionally
whenever a response exists; the only confidence gate in the path is `SIDEBAR_SHOW_THRESHOLD = 0.6`
for _sidebar visibility_ (`index.ts:660`), which does not gate DOM mutation or card reorder. At the
first call the distribution is BASE*PRIOR (neutral 0.37) + device + referrer hints, so a single hint
can tip argmax into a real archetype at ~0.05–0.10 confidence and reshuffle the page. \_Why it
matters:* the "wrong-archetype early reshuffle" that erodes trust. _Fix:_ gate `applyDirectives`
(especially `reorder`) behind `confidence ≥ ~0.5` or `signal_count ≥ 2`; keep neutral/below-floor a
no-op. **Effort: S.** → FOLLOW-343

**F-02 | High | Profile Engine — `archetype_embeddings.embedding` permanently NULL; cosine path is
dead code.** `packages/db/migrations/0005_seed_archetype_embeddings.sql:1-3` seeds 18 rows with
`embedding NULL` ("filled in by the Modal daily job"); a repo-wide grep finds **no code that ever
writes that column** (no `/api/archetype/embed` route, no Modal job). `getArchetypeEmbedding()`
always returns NULL → `affinityScore()` falls back to `deterministicScore`
(`apps/decision-api/src/lib/reorder.ts:309-312`,
`apps/control-plane/src/app/api/adapt/route.ts:496-499`). _Why it matters:_ the entire
vector-matching layer advertised in §F is non-functional; the "data network effect / MOAT" has no
live substrate. _Fix:_ build the embedding-population job (embed the 18 seed descriptions via
`text-embedding-3-small`, write the column) — or remove the cosine branch and stop advertising it.
**Effort: M (build) / S (remove).** → FOLLOW-341

**F-03 | High | Decision Engine — Thompson bandit optimizes behaviorally identical arms.**
`apps/control-plane/src/app/api/adapt/route.ts:909-925`. `runDecisionTree()` runs before
`thompsonSample()` and never receives the variant; `getPlaybook()` keys only on archetype, so
control/v1/v2 produce byte-identical directives. The bandit, ClickHouse logging, feedback ping, and
Beta updates all function — but there is nothing to optimize, so any "winning variant" in the
dashboard is noise. (Playbooks already carry ≥3 copy variants per slot — `playbooks.test.ts:97` —
they're simply not variant-indexed.) _Fix:_ thread `selectedVariant` into `runDecisionTree`/
`getPlaybook` to select distinct copy per arm. **Effort: M.** → FOLLOW-342

**F-08 | Medium | Decision Engine — `page_type` validated but never consumed; `tier` hardcoded.**
`route.ts:174` validates the enum; it is never read again. `tier: 1` is hardcoded in all three
response arms (`:807,833,1008`). A `listing_detail` and a `search` page get identical treatment, and
the analytics `tier` column is a constant. (Note: the _SDK_ side now correctly derives pageType via
`detectPageType`, `index.ts:137`, so the 06-04 SDK-side F-08 is fixed; this is the server side.)
_Fix:_ plumb `page_type` into directive selection. **Effort: M.** → FOLLOW-345

### 4.2 Architectural / conceptual issues

**F-09 | High | Conceptual — single-winner argmax on overlapping, thin-signal archetypes is
unstable.** `core/intent.ts:721-734` (`classifyFromProbabilities`). Several archetypes overlap
heavily (`upsizer`/`family_buyer`; `downsizer`/`retiree_relocator`/`empty_nester`;
`yield_hunter`/`portfolio_builder`; `lifestyle_expat`/`diaspora_buyer`/`second_home_buyer`). With
BASE*PRIOR neutral 0.37 and a flat 0.04 elsewhere, early behavioral nudges produce razor-thin
margins; argmax flips between near-ties cycle to cycle. \_Why it matters:* the same buyer can
reshuffle between two adjacent archetypes on consecutive refetches. _Fix:_ require a margin gap
before switching, or blend the top-2 archetypes' playbook priorities rather than picking one.
**Effort: M (+ product decision).** → FOLLOW-344

**F-06 | Medium | Profile Engine — 8 of 18 archetypes have no passive behavioral discriminator.**
`core/intent.ts:291-393` (`SIGNAL_LIKELIHOODS`). Only ~9 archetypes get a specific push from passive
signals (scroll/view/cta/dwell). The other 8 —
`commercial_investor, golden_visa_buyer, vacation_rental_investor, remote_worker, downsizer, retiree_relocator, diaspora_buyer, student_parent`
— are reachable only via explicit `filter.applied`/`feature.expanded`/`micro_poll`/quiz/chat events
that most ambient sessions never fire. `device_type` gives only a coarse investor↔own-use split.
_Why it matters:_ without quiz or chat, a third of the archetype space is unreachable on real
browsing. (Improved from 06-04's "15/18 blind.") _Fix:_ add passive discriminators (e.g.
dwell-on-commercial, gallery/location behavior) or accept these as quiz/chat-only and document it.
**Effort: M.** → FOLLOW-344

### 4.3 Missing pieces and dead ends

**F-04 | High | DOM Adaptation — SDK never self-annotates `data-estalara-slot`; adaptation is
invisible on un-instrumented pages.** `packages/sdk/src/core/adapt.ts:465`,
`adapt-description.ts:276,303`; no `setAttribute('data-estalara-slot', …)` exists anywhere in
`packages/sdk/src` (non-test). Auto-detect techniques only emit selector strings for the
control-plane schema; they are never fed back to annotate the live DOM. The "Plan A" runtime
annotation step (read curated/detected `slot_selectors` → annotate DOM before `fetchDirectives`)
**does not exist**. _Why it matters:_ this is the single biggest gap between "pipeline exists" and
"buyer sees adaptation," compounded by ESC-020 (app.estalara.com hooks not deployed). _Fix:_ add a
throw-safe, non-destructive SDK bootstrap that resolves `slot_selectors` →
`el.setAttribute('data-estalara-slot', name)` (skip if already present) before the first directive
fetch. **Effort: M.** → FOLLOW-340

**F-05 | High | Chat Integration — chat NLP engine has no production trigger.**
`apps/intent-engine/src/main.py:31-60` (`process_chat_message` is a bare `@app.function` — no
`web_endpoint`, no consumer); `apps/stream-consumer/src/consumers/events.py` only validates and
inserts to ClickHouse (zero chat/intent routing). The real 349-LOC extractor (`nlp.py`), the Redis
shadow reader (`chat-intent-cache.ts`), and the SDK consumer (`applyChatIntentPrior`, exported
`index.ts:1407`) are all built — but the middle hop is missing, so the shadow key is never written
and the whole bridge is dead in prod. _Mitigation:_ the engine is shadow-only by design this sprint
(its own docstring says no live adaptation reads it), so this is an activation gap, not a
regression. _Fix:_ route `chat.message.sent` to `process_chat_message.spawn(...)` from the
stream-consumer or via a Modal `web_endpoint` the ingest worker calls (mirror the `intent.snapshot`
waitUntil pattern). **Effort: M.** → FOLLOW-346 (gated on CEO decision to leave shadow mode)

**F-10 | High | Analytics — legacy `/dashboard/analytics` `lift` + `summary` routes fabricate
metrics on ClickHouse failure.** `api/dashboard/analytics/lift/route.ts:159-181,256-264` and
`summary/route.ts:94-98,150-151`. Both return `null` on `!res.ok` _and_ on any thrown error, then
serve a deterministic mock z-test / "significant" lift at **HTTP 200 with no `data_source` flag and
no MOCK badge**. A configured-but-failing ClickHouse silently shows operators fake conversion-lift
significance — the exact Rule K.2 failure the pilot route was hardened against. Tracked as
FOLLOW-329, **not fixed**. (The _pilot_ cta-lift path is correct and fail-loud — this is only the
legacy analytics dashboard.) _Fix:_ distinguish "CH unset" (mock OK) from "CH set but failed" (HTTP
500 + Sentry); add provenance + badge. **Effort: S.** → FOLLOW-329 (already filed; this audit
confirms STILL OPEN)

## 5. Conceptual Soundness Review

- **Archetype model coherence — weak on exclusivity.** The 18 archetypes are not mutually exclusive
  (F-09). The quiz v2.0 tree forces a single leaf cleanly, but behaviorally the overlapping pairs
  compete for the same thin signals, and single-winner argmax between near-ties is unstable.
  Recommendation: move adaptation to a top-2 blended profile, or enforce a switch-margin. This is
  the one place where the _specification_, not just the code, needs a decision.
- **Signal sufficiency — insufficient without quiz/chat.** Passive browsing resolves a coarse
  investor↔own-use axis plus ~9 archetypes weakly. Reliable fine-grained matching realistically
  requires the quiz (genuinely implemented, 0.85 direct assignment, drift-guarded — the strongest
  part of the engine) or chat-intent priors (built but un-triggered, F-05). The product's "detect
  intent without asking" promise (§Snapshot.3) is still only weakly true.
- **DOM adaptation UX — safe, but gated and currently invisible.** By construction the apply path is
  XSS-safe (`textContent`/`createElement` only, `[data-estalara-*]` selector allowlist, fully
  try/caught, never throws onto the host). It will feel natural _if_ slots exist and a confidence
  floor is added. Today, on an un-annotated page, it does nothing (F-04).
- **Measurement plan — real and trustworthy on the pilot path; fabricating on the legacy path.**
  `/api/pilot/cta-lift` runs parameterized ClickHouse joins, a correct two-proportion z-test
  (`lib/z-test.ts`, A&S erf, pooled proportion), N-guards, fails loud, and the `/dashboard/pilot`
  page badges mock vs live. Durable `conversion_labels` capture prediction↔outcome pairs (with
  `features_snapshot`/`model_version`/`lead_id`) for future LoRA training. The §T Conversion Label
  Loop is genuinely logged from day 1. The gap is F-10 (legacy analytics fabricates) and that the
  lift it would measure is currently driven by placebo bandit arms (F-03) and hash ordering (F-02).
