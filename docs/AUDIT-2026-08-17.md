# Audit 2026-08-17 — full user + admin walkthrough (localhost + prod)

**Scope (CEO brief):** every archetype must produce the right DOM; measure and minimise
archetype-detection → DOM latency; verify Demo Mode; verify every surface on `admin.estalara.com`;
verify that un-checking _Personalization_ returns the listing to its original copy; verify the quiz
resolves the correct archetype; verify that editing quiz questions on admin actually reaches the
LLM/archetype mapping. Goal: certainty that putting the SDK on production `app.estalara.com` will
work on day one when the topic is handed to Rafał.

**Method:** driven as a real buyer in the browser on `:5173` (local Estalara app + SDK + local
decision harness), then as an operator on the live `admin.estalara.com`, plus direct HTTP probes of
the production `/api/adapt` and quiz endpoints.

**Verdict:** 🟡 **YELLOW.** The buyer loop works end-to-end on localhost — quiz → archetype →
adapted headline + description — and after this audit's optimisation it is fast (~40 ms). Three P1
defects stand between that and a clean production hand-over, one of them on the production control
plane itself (the LLM path is down and every adapt is a static template fallback). Nothing found is
architectural; all three are bounded fixes.

## 2. What this audit changed (already committed as `1687d24b`)

Branch: `devops-engineer/FOLLOW-1017-mock-harness-demo-parity`.

The latency target and the "demo shows the wrong buyer" bug were both fixed inside the local
decision harness (`scripts/dev/mock-decision-server.mjs`). Four changes:

1. **Parallel generation.** `/adapt` ran the description call and then the headline call
   sequentially and blocked on both: 9.5 s from quiz completion to DOM. They now run in parallel —
   cost is `max(desc, headline)` ≈ 6–8 s on a cold cache. The fit-gate verdict still comes from the
   description call and still discards the headline on NEUTRAL. Concurrent `/adapt` and
   `/adapt/description` for the same `(listing, archetype)` are deduped onto one in-flight
   generation instead of racing two.
2. **Prewarm (default on).** At boot the harness generates all 17 personas for the demo listing,
   keyed by the **listing UUID** — the key the SDK actually sends. (Prewarming the slug alone left
   every real SDK request a cache miss; that subtlety is why the first attempt looked like it did
   nothing.) Measured result: quiz completion → adapted DOM **~40 ms**.
3. **Complete personas.** The five §D.6 "chat-only" archetypes are in fact quiz-reachable leaves of
   the default tree (Investment → Commercial; golden visa, retiree, diaspora, student via
   cross-border). Without personas the harness silently substituted the switcher's archetype — the
   demo showed copy for a _different_ buyer than the quiz had resolved. All 17 now generate.
4. **`/quiz/public-config` proxy.** Locally the SDK's `decisionApiUrl` is the harness, so the quiz
   config request 404'd and the SDK fell back to its **built-in** tree — meaning quiz edits made on
   admin never reached the local demo, and any local "quiz test" was testing hard-coded questions.
   The harness now proxies the live control plane (60 s cache, because the SDK's init fetch has a 1
   s timeout).

> Read #4 as a finding about **how we test**, not only about the harness: before this fix, local
> quiz verification was structurally incapable of catching an admin-side quiz regression.

## 3. Defects found — with fix paths

Filed as stubs in `backlog/FOLLOW_UPS.md` (commit `4ddb4dbc`).

### P1 — FOLLOW-1022 · production `/adapt` is serving static fallbacks, not LLM copy

`POST https://admin.estalara.com/api/adapt` (demo-override active) returns
`"source": "playbook_fallback_llm_unavailable"`. Every production adapt decision is a static
playbook template. Demo Mode's banner promises "generated with Haiku 4.5" and delivers a template —
so a demo to a client today would _look_ live and _be_ canned.

**Fix path:** check the Anthropic key in the **Vercel** env for the control plane first (Vercel env
≠ Doppler — this exact class bit us before), then the llm-gateway URL/timeout, then whether this is
an intentional cost gate. If intentional, the Demo Mode banner and Platform Settings copy must stop
claiming live generation. Close with a canary that asserts `source ≠ *_llm_unavailable`, so a silent
regression becomes loud.

### P1 — FOLLOW-1018 · unresolved `{token}` placeholders are painted literally

`interpolatePlaceholders` (`packages/sdk/src/core/adapt.ts:713`) resolves `{token}` from
`data-estalara-*` attributes and, when a token has no source, **leaves it literal** and only emits
`adapt.skipped`. The live prod probe returned the directive
`"Exceptional Residence — {key_luxury_feature}"`; `app.estalara.com` carries no such attribute, so a
buyer would literally read `{key_luxury_feature}` in the headline.

This is P1 _because of_ FOLLOW-1022: the token-bearing playbook path is currently the default, not
the edge case.

**Fix path:** whole-directive skip when any token is unresolved (never paint raw braces), red-first
unit test, then audit all 17 playbooks so each token either has a documented attribute source or the
line is rewritten token-free.

### P1 — FOLLOW-1019 · opting out of personalization does not restore the original copy

Browser-verified: complete quiz → headline and description adapt → un-check the §H.9 Personalization
toggle → **both stay adapted** until a full page reload. The `onChange` handler only stops _future_
directives; its comment claims "the tenant-default DOM is already visible", which is false
mid-session. A visitor who just declined profiling keeps reading profiled content — exactly the
behaviour the brief asked me to confirm, and it fails.

**Fix path:** the restore primitives already exist (original capture + the cross-listing restore
used on navigation). On opt-out, actively revert both axes through that same path, clear the adapted
fingerprints, correct the false comment, and cover it with an E2E (opt-out restores without reload;
opt back in re-adapts).

### P2 — FOLLOW-1020 · quiz analytics are silently wrong

`postQuizCompletionPing` sends only `{ session_id, resolved_archetype, language }`. The staff Quiz
Completions viewer renders BRANCH and Q1/Q2/Q3 columns from data the SDK never sends: a real full
Investment→Rental→Steady walk shows as **"neutral (Q1 skip)"** with dashes, and the Branch Split
card counts it as a skip.

**Fix path:** extend the ping with the answer path (question ids + answer indexes) and branch — the
storage columns already exist; render "not reported" for legacy rows and exclude them from the
Branch Split maths.

### P3 — FOLLOW-1021 · admin quiz editor still labels a deleted trigger

The editor says "Sticky Trigger Placement — where the quiz trigger button anchors". FOLLOW-1015
deleted that button; the value now anchors the auto-opening quiz **card**. Operator-facing copy must
say what it actually controls.

### P3 — FOLLOW-1023 · tracer robustness

(a) First visit to Session History after idle returned `API error [500]: ClickHouse query failed`;
the identical request succeeded ~20 min later — the ClickHouse Cloud idle-wake pattern. The route
should retry once on a cold-start-shaped failure before showing a red banner. (b) `intent_events` is
empty all-time for the pilot tenant while `adaptation_decisions` has real rows — consistent with "no
production session ever crossed the 5-signal snapshot threshold", because there is no SDK on
`app.estalara.com` yet (ESC-020). It means the SDK → ingest → ClickHouse tracer pipeline **has never
been proven in production**.

## 4. Not defects — not yet built / already known

- **ESC-020 (open): there is no SDK on production `app.estalara.com`.** This is the single blocker
  between everything above and real users. Every "prod" finding here was probed through the control
  plane API, not through a live buyer session.
- **FOLLOW-1012:** flipping a quiz on/off takes up to ~6 minutes to reach a buyer (300 s cache + 60
  s SWR) and no surface says so. Not a regression; an expectation gap.
- **FOLLOW-1016:** the auto-opening quiz card overlaps whatever sits in its corner on a tenant page,
  and the SDK cannot know what that is. Decision needed (occlusion detection vs. operator-configured
  with a warning), plus a mobile check.
- The local decision harness is a **mock**: it now mirrors prod's prompt, fit gate and quiz config,
  but the parity is maintained by hand. Treat harness-green as necessary, not sufficient.
