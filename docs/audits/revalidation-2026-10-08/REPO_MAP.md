## Jak czytać ten zapis

Przegląd objął wszystkie aplikacje i pakiety przez ich wejścia, główne implementacje i połączenia.
**Nie przeczytano każdego pliku repozytorium ani każdego pliku implementacyjnego w całości.** Przy
dużych plikach odczytywano zakresy i rozwijano zależności wokół ocenianych zachowań. Dlatego ten
materiał stanowi ponowną weryfikację wskazanych kontraktów i mapę całego repo, a nie pełną
certyfikację bezpieczeństwa lub ukończone WP00 dla wszystkich przyszłych zmian.

- [inventory.json](inventory.json) zawiera kompletny spis 1560 śledzonych plików na powyższym SHA.
  Spis nie jest dowodem lektury.
- [reading.jsonl](reading.jsonl) zapisuje część odczytanych zakresów, SHA-256 plików i sposób
  odczytu. Nie obejmuje wszystkich bezpośrednich odczytów shell. Część długich wyników narzędzia
  była ucięta; rejestr żądanych zakresów nie dowodzi, że każda linia została dostarczona do analizy.
  Niektóre odczyty pomijały puste linie i samodzielne komentarze.
- Poniższe tabele podają faktycznie przeglądane ścieżki i ograniczenia. „Wybrane testy” oznacza
  odczyt lub wykonanie wskazanych testów, nie całego katalogu. Świeże wykonania są osobno w
  EVIDENCE/REVIEW.
- Każdy przyszły PR wymaga odczytania pełnych aktualnych plików, które zmienia, ich
  callerów/consumerów i właściwych testów. Tego obowiązku nie zastępuje niniejsza mapa.

Ścieżki w tabelach są względem repo root. Zapis folderu z wyliczeniem plików oznacza te konkretne
pliki, nie wszystkie pliki folderu.

## Połączenia sprawdzone przez koordynatora w źródle

1. **SDK → ingest:** `core/events.ts` tworzy transport; `router.ts` uruchamia middleware przed
   `handlers/events.ts`; handler używa `EventSchema`, nie legacy validatora. `event.ts` dopuszcza
   zakres timestamp/field size, którego dalsza serializacja/kolejka nie obsługują.
2. **Snapshot → tracer:** SDK envelope → ingest `intent-snapshot.ts` → JSON string w polu JSONB →
   list reader oczekujący object. Połączenie istnieje, format nie pasuje. Current event.ts jest
   mylony z początkiem sesji.
3. **Chat → adapt → SDK:** host listener → ingest dispatch → Python extraction/Redis → TS chat cache
   → POST response → `applyChatIntentPrior` → follow-up warunkowany archetypem. Wartość confidence
   może zmienić się bez zmiany archetypu. Probe rzeczywistego init dowodzi scheduler/storage, ale
   mockuje zewnętrzny hop.
4. **Listing → generated description → cache → DOM:** backend grounding → description request →
   Python job → Redis + callback PG → cache reads/warm/backfill → SDK description. Nie ma wspólnej
   wersji źródła na wszystkich tych granicach; numeric refusal nie zatrzymuje FIT.
5. **Listing → directives:** backend facts/context → TS gateway → numeric/name checks/judge → route
   directives → SDK. Kontrolowane provider outputs przechodzą rzeczywisty gateway z niepopartymi
   cechami i jednostkami.
6. **Authentication → mutations:** auth package → session-auth/tracer-auth lub bezpośredni verifier
   → konkretne routes. Weryfikacja tenant nie zastępuje write rank; embed daje dodatkowy dowód
   wykonania gałęzi zapisu.
7. **Telemetry → SQL → UI:** events/decisions → rollup/lift/inquiry queries → dashboard mapping.
   Inne cohorts, nieprawidłowa kardynalność, CTA zamiast adopted conversion, null zamieniane na 0.
   Source review; poprzednie liczby syntetycznego CH nie zostały odtworzone.
8. **DSR → magazyny:** initiate zależy od tabeli bez aktywnego writera → OTP → access/erase →
   PG/CH/Redis. CH gubi tenant; Redis ignoruje część błędów; OTP read/check/update pozwala
   przekroczyć cap. Export limit i capability nie mają kompletnego continuation.

## Jawne wyłączenia i rzeczy nieudowodnione

Nie czytano liniowo: vendor/node_modules, lockfile internals, generated build output, binariów,
całych archiwów backlog/audit, wszystkich styli/UI bez wpływu na oceniane kontrakty, każdej
historycznej migracji/operator script, każdego testu i każdej niewykorzystywanej gałęzi endpointów.
Wyłączenia wynikają z ukierunkowanego audytu kontraktów, nie z założenia, że te pliki są poprawne.

Niedostępne lub nieweryfikowane: kod zewnętrznego hosta pilota, oryginalne `/workspace/audit-*`,
konfiguracja/secrets usług, środowiska produkcyjne, migracje/granty/KV/live Redis, live model
quality, realne dostarczenie maili, Sentry delivery, p95, wolumen kupujących i causal uplift. Nie ma
podstaw do ich oznaczenia PASS.

W wyniku przeglądu żaden moduł first-party nie został pominięty w mapie. To nie oznacza, że każde
możliwe przeoczenie zostało wyeliminowane. Mocne wnioski i ich rzeczywistą głębokość dowodu
ogranicza [EVIDENCE.md](EVIDENCE.md).
